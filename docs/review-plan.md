# План code review: модуль расчёта стоимости корзины и скидок

## 1. Объект и границы ревью

**Объект ревью:** `src/discount.py`, функция `calculate_cart_total(cart_sum, tier, promos)`.

**Назначение функции:** рассчитать итоговую стоимость корзины с учётом базовой скидки для крупных заказов, промокодов, уровня лояльности и ограничения максимальной скидки.

Ревью проводится для алгоритма, представленного в UML Activity Diagram (`docs/uml_diagram.png`). Проверяющие должны сопоставить реализацию с последовательностью действий и ветвлениями на диаграмме.

## 2. Цели ревью

1. **Точность расчётов.** Проверить правильность порядка применения скидок и итоговой суммы.
2. **Корректность применения скидок.** Убедиться, что базовая скидка применяется только при `cart_sum > 15000`, промокоды `SUMMER` и `VIP` обрабатываются по заданным правилам, а скидка уровня лояльности применяется для соответствующего `tier`.
3. **Защита от фрода и некорректных данных.** Проверить, что функция не принимает некорректные суммы, неизвестные уровни лояльности и неподдерживаемые структуры списка промокодов; исключить возможность получить итоговую цену ниже установленного порога.
4. **Сопоставимость реализации и документации.** Убедиться, что код, тесты и UML-диаграмма описывают одну и ту же бизнес-логику.

## 3. Проверяемые правила бизнес-логики

Ревьюер проверяет следующие правила и граничные случаи:

- Начальная цена `price` равна `cart_sum`.
- Если `cart_sum > 15000`, применяется коэффициент `0.85`; при сумме ровно `15000` эта скидка не применяется.
- Для каждого промокода из `promos`:
  - `SUMMER` уменьшает текущую цену на 500;
  - `VIP` умножает текущую цену на `0.90`;
  - неизвестный промокод не должен менять цену.
- После обработки промокодов:
  - при `tier == 1` цена умножается на `0.97`;
  - при `tier == 2` цена умножается на `0.93`;
  - для остальных допустимых значений дополнительная скидка не применяется.
- Если рассчитанная цена меньше `cart_sum * 0.70`, итоговая цена ограничивается значением `cart_sum * 0.70`.
- Промокоды применяются последовательно, в том порядке, в котором они переданы в `promos`.

## 4. Измеримые критерии приёмки

| Критерий | Что проверяется | Условие приёмки |
|---|---|---|
| Магические числа | Порог 15000, коэффициенты 0.85/0.90/0.97/0.93/0.70 и сумма 500 | Значения вынесены в именованные константы либо их использование явно документировано и согласовано |
| Валидация входных данных | `cart_sum`, `tier`, `promos` | Есть проверки типа и допустимых значений; некорректные данные обрабатываются предсказуемо |
| Точность денежных расчётов | Операции с ценой и округление | Выбран и последовательно применяется подходящий тип для денежных значений; правила округления документированы |
| Граничные случаи | 15000, значения около порога, отсутствие/повтор промокодов, неизвестный промокод, минимальная цена | Есть отдельные тесты для каждого перечисленного случая |
| Покрытие тестами | `src/discount.py` | Покрытие тестами — **более 80%** |
| Соответствие UML | Ветвления, цикл, порядок применения скидок | Все существенные ветви алгоритма отражены в коде и проверены тестами |
| Качество кода | Читаемость, имена, отсутствие дублирования | Нет критических замечаний линтера; логика разбита и прокомментирована настолько, насколько это необходимо |

**Примечание:** требование «отсутствие магических чисел» означает, что бизнес-параметры скидок должны быть объявлены как именованные константы. Их значения должны совпадать с утверждёнными правилами алгоритма.

## 5. Обязательные тестовые сценарии

Перед одобрением изменений должны быть проверены как минимум следующие сценарии:

1. Корзина меньше 15000 — базовая скидка не применяется.
2. Корзина ровно 15000 — базовая скидка не применяется.
3. Корзина больше 15000 — применяется скидка 15%.
4. Промокод `SUMMER` — из текущей цены вычитается 500.
5. Промокод `VIP` — текущая цена умножается на 0.90.
6. Несколько промокодов — скидки применяются последовательно.
7. `tier == 1` и `tier == 2` — применяются соответствующие коэффициенты.
8. Неизвестный промокод и уровень без дополнительной скидки — цена не изменяется этим правилом.
9. Итоговая цена ниже 70% исходной — срабатывает нижняя граница.
10. Пустой список промокодов и некорректные входные значения — обрабатываются согласно контракту функции.

## 6. Участники и роли

| Участник | Роль | Ответственность |
|---|---|---|
| Автор изменений | Разработчик | Реализует алгоритм, добавляет тесты, исправляет замечания |
| Ревьюер | Ведущий разработчик | Проверяет бизнес-логику, читаемость, архитектуру и соответствие UML |
| QA-инженер | Тестировщик | Проверяет граничные случаи, тестовое покрытие и воспроизводимость дефектов |
| Аналитик | Владелец требований | Подтверждает правила скидок и разрешает неоднозначности требований |
| Ответственный за слияние | Maintainer | Проверяет прохождение CI и наличие необходимых одобрений перед merge |

В учебном проекте один человек может выполнять несколько ролей, но ответственность каждой роли должна оставаться различимой.

## 7. Порядок проведения ревью

1. Автор создаёт Pull Request с изменениями `src/discount.py` и тестов.
2. Автор прикладывает краткое описание изменений и указывает, какие правила алгоритма затронуты.
3. Ревьюер сверяет реализацию с UML-диаграммой и критериями из этого документа.
4. QA-инженер проверяет тесты, граничные случаи и покрытие.
5. Автор исправляет замечания отдельными коммитами и отвечает на комментарии.
6. Pull Request одобряется только после устранения блокирующих замечаний и успешного прохождения CI.

## 8. Эскалация при разногласиях

1. При споре о соответствии кода требованиям участники сначала сверяют спорный пункт с описанием алгоритма и UML-диаграммой.
2. Если требование допускает несколько трактовок, вопрос передаётся аналитику для письменного уточнения бизнес-правила.
3. Если разногласие касается технической реализации, окончательное решение принимает ведущий разработчик совместно с ответственным за слияние.
4. Блокирующее замечание нельзя закрывать простым несогласием: автор должен исправить код либо добавить согласованное обоснование и тест.
5. Решение и его обоснование фиксируются в комментариях Pull Request. До разрешения блокирующего вопроса Pull Request не сливается.

## 9. Условия одобрения

Pull Request может быть одобрен, если:

- все обязательные проверки CI завершились успешно;
- тесты проходят, покрытие `src/discount.py` превышает 80%;
- входные данные валидируются;
- денежные расчёты и округление реализованы последовательно;
- нет неразрешённых блокирующих замечаний;
- реализация соответствует бизнес-правилам и UML-диаграмме.
